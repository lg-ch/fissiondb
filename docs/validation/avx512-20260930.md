# Runtime AVX-512BW kernels: exactness and MS MARCO retrieval

The engine now selects AVX-512F/BW for signed int8 routing and sufficiently
wide TQ1 scoring when the CPU and operating system expose those features.
AVX2, scalar and ARM paths remain available in the same source. No index
conversion or global AVX-512 compiler flag is required. The wider integer
kernels preserve the results exactly; floating-point arithmetic is unchanged.

## Same-host retrieval comparison

The Kamatera guest exposes four vCPUs identified as Intel Xeon Sapphire Rapids
(family 6, model 143), under KVM. AVX2 and AVX-512F/BW are exposed; VNNI is not.
This virtual CPU description does not identify a retail CPU SKU or guarantee
a sustained physical clock. The guest storage is a non-rotational virtual block
device; its underlying physical storage and host contention are not controlled.

All four passes used the same binary and the complete, unchanged MS MARCO
index: **113,520,750 vectors, 1024 dimensions, 200,000 representatives**,
two assignments per vector, **1,536 probes and 400 reranks**. Each pass used the
same 600 real query-to-document queries, exact ground truth and shuffled order.
The query panel was reused during development.

The process had one query thread pinned to guest CPU0, a decimal 1 GB cgroup
limit and no swap. Residual reads used O_DIRECT with overlapping 64-cell batches.
The harness requested page-cache eviction for originals and residuals before
each query; hardware device caches were not flushed. There was no ingestion or
HTTP serving. Timings cover the native retrieval call inside the guest, excluding
index loading, SSH and client network transit.

`FISSIONDB_DISABLE_AVX512` was the only engine setting changed, in A/B/B/A order:

| Pass | Backend | Median | p95 | Recall@10 |
|---:|---|---:|---:|---:|
| 1 | AVX2 | 127.61 ms | 177.71 ms | 96.25% |
| 2 | AVX-512BW | 111.57 ms | 164.18 ms | 96.25% |
| 3 | AVX-512BW | 112.83 ms | 143.82 ms | 96.25% |
| 4 | AVX2 | 121.77 ms | 164.20 ms | 96.25% |

The average of the two pass medians fell from **124.69 to 112.20 ms (10.0%)**.
Every query had exactly the same ordered IDs, FP32 scores, candidate entries and
code bytes in all four passes. Mean traffic remained 138.39 MB and mean candidate
entries 1,845,178 per query. The returned IDs also matched the earlier ARM panel
for all 600 queries; maximum cross-architecture score difference was 1.43e-6.

| Mean timer, pooled within backend | AVX2 | AVX-512BW |
|---|---:|---:|
| Representative routing | 27.44 ms | 24.33 ms |
| Candidate scoring | 78.88 ms | 72.63 ms |
| Visible code IO | 15.08 ms | 11.92 ms |
| Exact rerank | 6.73 ms | 6.26 ms |
| Native call wall time | 128.39 ms | 115.36 ms |
| Process CPU time | 120.45 ms | 108.64 ms |

IO and scoring overlap; these stage timers are not independent additive costs.
IO and rerank times also varied even though their implementations did not change.
The 10% end-to-end difference is an observation on this guest, not an isolated
instruction-throughput estimate or a universal speedup. An additional CPU-only
A/B/B/A microbenchmark measured approximately 6% lower median time for both
200,000-center routing and scoring 1,048,576 residual codes.

The first pass reached the rounded 999,997,440-byte cgroup cap, including opening
the index, and recorded memory-limit reclaim events. Later pass peaks were
330.11, 355.30 and 306.81 MB respectively, without such events. All passes had
zero OOM events and zero swap. Page-cache ownership and opening behavior affect
these peaks; they do not establish a backend-specific RAM saving.

The guest reported zero CPU steal during these passes. This does not rule out
host interference, memory bandwidth differences or frequency effects. CPU time
accounts for most of the measured latency. The earlier GB10 result of 52.69 ms
therefore cannot be recovered by subtracting client network time: that time is
already excluded. A wider instruction set alone does not guarantee equal latency
across the two processors or across cloud and dedicated deployments.

## Validation and controls

- Full suite: **205 passed on x86**; **202 passed and 3 x86-specific skips on ARM**.
- Focused AddressSanitizer/UndefinedBehaviorSanitizer suite: **74 passed on x86**.
- Standalone instrumented checks: **229,376 exact kernel comparisons**, including
  every dimension from 1 through 2048, signed extremes, unaligned addresses,
  nontrivial strides, all half-float bit patterns and protected-page tail checks.
- An adaptive 768d collection produced identical representatives, encoded cells,
  candidate counts, IDs and scores with AVX2 and AVX-512 after inserts, splits,
  an update and a deletion.

`integer_backend()` exposes the selected integer backend. Set
`FISSIONDB_DISABLE_AVX512=1` before process startup to compare the narrower path.
The environment setting is read once at library load. Short inputs can still use
AVX2; TQ2/TQ4, floating-point operations and ARM kernels are unchanged.

Source base: `5e2a506c21f4062a785f4dc160b36eda912e3ffd`, plus the AVX-512 changes
published with this report. The tested library SHA-256 is
`7ce611997dde6bf9c526921ff0f2dbdcc935fa9fa6ba1a7577800b809c94fb6d`.
